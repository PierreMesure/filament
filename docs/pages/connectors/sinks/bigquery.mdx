The BigQuery sink (**alpha**) writes each resource to a typed BigQuery table.
It supports snapshot, incremental, and CDC pipelines using Parquet load jobs
staged through short-lived tables in the destination dataset.

## BigQuery setup

Authentication uses Google Application Default Credentials, so the connection
has no credential fields. On GKE, use Workload Identity. For local development,
run `gcloud auth application-default login` before starting Filament.

The credential needs to run jobs in the configured project and to create and
modify datasets and tables. The simplest grant is:

- `roles/bigquery.jobUser` on the project, and
- `roles/bigquery.dataEditor` on the project, or on the destination dataset if
  it already exists.

Filament runs `CREATE SCHEMA IF NOT EXISTS` for the pipeline dataset, so
project-level `dataEditor` (or `roles/bigquery.user`) is required when the
dataset does not exist yet.

`TestConnection` authenticates and executes `SELECT 1`.

## Configuration

| Field | Scope | Default | Description |
| --- | --- | --- | --- |
| `project_id` | Connection | — | Required. Google Cloud project used for BigQuery jobs. |
| `location` | Connection | — | Optional dataset and job location, such as `us-central1`. Applied when Filament creates the dataset; afterwards the dataset's own location wins. |
| `dataset` | Pipeline | — | Destination dataset. Empty defaults to the normalized source connection name. |

The sink prefers batches no larger than 100,000 rows or approximately 256 MiB,
whichever limit is reached first.

## Supported write modes

The sink advertises `full_replace`, `full_append`, `full_upsert`,
`incremental_append`, `incremental_upsert`, `incremental_delete`, `cdc_append`,
and `cdc_merge`. See
[replication modes](/pages/guides/concepts/replication-modes).

- Replace loads the snapshot into a run-scoped replacement table and swaps it
  into the destination atomically at commit.
- Append inserts each batch directly into the destination.
- Upsert, delete, and merge apply each batch with one BigQuery `MERGE`. These
  modes require a primary key.

## Table management

Before extraction, `EnsureSchema` runs per resource:

1. Create the destination dataset and typed table if they do not exist.
2. Add missing columns with `ADD COLUMN IF NOT EXISTS`.
3. For replace, create a run-scoped typed replacement table with a seven-day
   expiration.

Schema evolution is add-only. Existing columns are not dropped, renamed, or
altered. Primary keys are declared `NOT ENFORCED`, as BigQuery requires, and
Filament uses the key columns to build deterministic merge conditions. BigQuery
limits primary keys to 16 columns and to key-eligible types, and schemas that
exceed either limit are rejected before extraction.

## Write mechanics and atomicity

Each Arrow batch is encoded as a Snappy-compressed Parquet file in memory and
loaded into a short-lived `_filament_load_*` staging table in the destination
dataset with a BigQuery load job. A typed query then moves the rows onward:
append and replace run one `INSERT INTO ... SELECT`, and key-based modes run
one `MERGE` that folds repeated keys within the batch to their final operation
before applying inserts, updates, and deletes. The staging table is deleted
after the typed write, with a seven-day expiration as the fallback if the
process terminates first. No external storage bucket is required.

Load and query jobs use deterministic job IDs derived from the run, batch, and
payload, so an exact retry reuses the already-completed BigQuery job instead of
loading the data twice.

Append and keyed writes become visible per batch, and no transaction covers an
entire pipeline run. Replace batches accumulate in the replacement
table, and `Commit` promotes each one with a single
`BEGIN TRANSACTION; TRUNCATE; INSERT; COMMIT` — the destination switches from
old to new contents atomically per resource.

The sink verifies each load job's output row count against the batch and
records the encoded Parquet checksum in the write receipt. This validates the
load boundary but does not query the committed table back from BigQuery.

## Failure behavior

An append run can leave successfully loaded batches in the destination after a
later failure. Upsert, delete, and merge runs can also leave completed batch
merges, but retries converge through the primary key. A failed replace leaves
the destination untouched: the replacement is staged in a separate table and
promoted only at commit, and `Abort` deletes the run's staging tables.
Additive schema changes are intentionally retained on abort.

## Troubleshooting

- `could not find default credentials`: Application Default Credentials are
  not available in Filament's environment. Attach a service account, configure
  Workload Identity, or run `gcloud auth application-default login`.
- `Access Denied` on jobs or datasets: confirm `roles/bigquery.jobUser` on the
  project and `roles/bigquery.dataEditor` on the project or destination
  dataset.
- `Not found: Dataset ... was not found in location ...`: the dataset exists in
  a different location than the connection's `location` value. Match the
  connection to the dataset's location or leave `location` empty.
- `dataset must contain 1 to 1024 letters, numbers, or underscores`: BigQuery
  dataset IDs do not allow hyphens or dots. Adjust the pipeline's `dataset`
  value.
